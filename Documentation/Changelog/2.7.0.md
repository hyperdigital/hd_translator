# Changelog 2.7.0

## New Features
- **Who was offered a translation, and who agreed.** The demand screen counted translate
  requests, which says how many people used the translation and never how many were asked. The
  banner that does the asking belongs to the site package, not to this extension, so it now
  reports the two events itself:

  ```javascript
  hdtranslator_recordBannerShown('de');      // every time the banner becomes visible
  hdtranslator_recordBannerAccepted('de');   // when the visitor agrees
  ```

  Two numbers are kept, because they answer different questions: **how often** the banner was
  shown and **how many visitors** that was. Fifty displays can be fifty visitors or one visitor
  on fifty pages. So `hdtranslator_recordBannerShown()` belongs on every display - the backend
  counts the displays and deduplicates the visitor behind them itself.

  The screen shows `Shown` (displays, hover for displays per visitor), `Offered` and `Agreed`
  (both visitors) and the rate between the last two, per language for the selected range, plus
  the total displays and the overall rate beside the other insights. A language the banner
  offered and nobody took now appears in the table although it has no requests at all - that is
  the case worth seeing. Until something reports, the screen says so instead of showing an empty
  column.

  Without those calls there is nothing but requests, and a banner that translates its own text
  through `hdtranslator_translateText()` makes being shown a request as well: offered and agreed
  are then the same row and nothing can separate them afterwards.

## Fixes
- A returning visitor whose page was translated entirely out of the browser cache never reached
  the translate endpoint, so the demand counter missed exactly the visitors who use the
  translation most. `hdtranslator_translateWholePage()` now reports a full cache hit, which
  writes the row a translate request would have written.

## Privacy
- Banner rows carry the same day-salted visitor hash as the counting rows and nothing else: one
  row per language, day, visitor and event. Somebody who meets the banner on five pages is one
  row, which is what makes the ratio of the two events a rate rather than a quotient of
  impressions. No address and no user agent is written, and `aiRequestStatistics` switches the
  whole thing off as before.
- The displays are counted in a second table that has no visitor column at all - one row per
  language, day and event - so counting how often the banner was shown adds nothing about who
  saw it. It is bounded by construction: a language-day has one row per event whatever the
  traffic.

## Changes
- The banner endpoint `_hdtranslator_banner` accepts only synchronized target languages and
  shares `requestsPerMinute` with the translate endpoint.
- The cache hit of `translateWholePage()` is reported once per language, tab and day: it only
  feeds the visitor row, which is written at most once a day per person anyway.
- Banner rows follow `aiRequestStatisticsRetention` and are not folded into months the way the
  counting rows are: the question is about the banner as it stands, and a year-old rate is about
  a banner that has since been reworded.

## Upgrade
- Run the database analyzer. Two tables are added, `tx_hdtranslator_ai_banner` and
  `tx_hdtranslator_ai_banner_count`; both start empty and fill once the banner reports.
- Nothing changes for an installation that does not call the two helpers, apart from the cache
  hit that is now counted.
